## Q1：routing table 如何確認是真的運作，不是假數值

驗證機制分三層：

**層一：PrintRouteReport（離線 path trace）**
- 呼叫 `PrintRouteReport`，列出每個 time slot 的完整路徑
- 輸出如 `0->10->9->20->31->32`，slot 3 起路徑改變（`<-- PATH CHANGED`）
- 路徑隨衛星移動後距離成本改變，不是 hard-coded

**層二：RunAvoidanceTest（ISL 斷開驗證）**
- 強制封鎖某條 ISL（`m_blockedEdges`），再跑一次 Dijkstra
- 確認路由自動繞開，不殘留被封鎖的 next-hop

**層三：ApplyRoutingTable 寫入 SNS3 Arbiter**
- 呼叫 `ClearNextHopEntries()` + `AddNextHopEntry()` + `SetArbiter()`
- 直接操作 SNS3 的 `SatIslArbiterUnicast`，封包轉發靠它決定出口
- 若路由沒寫進去，封包找不到出口會被 drop

## Q3：routing cost 具體說明，為何不用原本 SNS3 模組

### cost 計算公式

| 用途 | 函式 | 公式 |
|------|------|------|
| PrecomputeAllTables（離線） | `BuildISLGraph()` | `propCost = dist / C`（光速傳播延遲，單位：秒） |
| ApplyRoutingTable（動態重算） | `BuildISLGraphWithLoad()` | `totalCost = propCost + loadCost` |

`loadCost` 由 `UpdateLoadCosts()` 計算：
```
loadCost = EMA(queue_delay)
         = alpha × (nPackets × 1500 × 8 / linkRateBps) + (1-alpha) × prevLoadCost
```

### 為何不用 SNS3 原生 routing

原設計三個假設在閱讀 SNS3 原始碼後發現均不正確（記錄於 `DEC-001`）：

| 原設計假設 | SNS3 實際情況 |
|-----------|--------------|
| 路由走 `Ipv4StaticRouting` | ISL 封包繞過 IP 層，由 `SatIslArbiterUnicast` 決定出口 |
| 讀 `FqCoDelQueueDisc` 取得負載 | SNS3 用 device-level `DropTailQueue<Packet>`，未安裝 TC 層 |
| interface index = Ipv4 interface index | Arbiter 用的是 `GetIslsNetDevices()` 的 vector index |

SNS3 原生 ISL routing 沒有 Dijkstra、time-slot 切換、load-aware 重算，這些功能全部自實作。

## Q4：BH Phase 1 config=false 的原因

`sat-bh-helper.cc` 預設值：
```cpp
m_cfg.enableScheduler  = false;
m_cfg.enableObc        = false;
m_cfg.enableCacheQueue = false;
m_cfg.enablePrecoder   = false;
```

**設計原則（`sat-bh-example.cc:24`）：**
> `sat-bh-example.cc` 本身在 Phase 1→3 過程中不需要改，只有 `SatBhHelper` 內部隨 Phase 進展補實作。

Phase 1 的 `false` 讓 Helper 走 **synthetic slot driver**（`ApplySyntheticSlot`）：
- 用Helper 自己定時產生固定數字餵給 Metrics 驅動 BHTP 切換
- 讓 Metrics CSV pipeline 先跑通
- 不依賴還沒實作的 Scheduler / OBC

SNS3 原生 example（如 `sat-gw-handover-example.cc`）有相同概念，用 `Config::SetDefault("ns3::SatXxx::EnableFeature", BooleanValue(false))` 先關掉功能，逐步開啟。

## Q5：v1 / v2 results — static vs dynamic 的判斷

### 關鍵差異

| 版本 | 啟動輸出行 | 意義 |
|------|-----------|------|
| v1 | `Phase2(Scheduler=0 OBC=0)` | static BHTP + synthetic driver |
| v2 | `Phase2(Scheduler=1 OBC=1)` | Scheduler + OBC 介面走通（stub） |

### 兩版本 BHTP 輸出完全相同的原因

v2 的 Scheduler / OBC 在當時仍是 stub，BHTP 內容沒有改變。  
差別在於介面路徑已接通，待 Phase 2 實作填入後才會出現不同的 slot 分配。

**結論：**
- v1 = Phase 1 only，BHTP 建立後不再改變，OBC 由合成事件代替
- v2 = Phase 2 stub，介面已接通但實作未完成，輸出與 v1 相同

## Q6：Phase 1 v.s Phase 2

### Phase 1，`ApplySyntheticSlot`

```
每 T_s = 26.5ms
Helper 定時觸發 → 直接呼叫 Metrics::OnSlotActivated / OnSlotDeactivated
封包來源：Helper 自己 Create<Packet>() 憑空建立
負載數字：hard-coded（hotspot=0.80, non-hotspot=0.40）
換槽邏輯：syntheticSlotIdx++ 循環走 static BHTP
```
觸發來源不是任何硬體模擬，封包不是真實流量，負載不反映實際 queue 狀態。

### Phase 2，`SatBhObc` state machine

```
SatBhScheduler 根據 demand 計算新 BHTP
  → m_obc->ReceiveNewPlan(plan, propDelay)
  → OBC 依 plan->GetPeriodStart() 排程 EnterSlot(0)
  → EnterSlot → BeamActivateCallback → Metrics::OnSlotActivated
  → 服務窗結束 → BeamDeactivateCallback → Metrics::OnSlotDeactivated
```

OBC state machine：`IDLE → ACTIVE → SWITCHING → ACTIVE → WAIT_PLAN`

- OBC 有完整 state machine，狀態由 NS3 模擬時間驅動
- BHTP 由 Scheduler 根據每 beam 的實際 demand 計算
- propagation delay 被正確計入 `plan->GetPeriodStart()`
- Phase 3 開啟後，`BeamActivateCallback` 還會觸發 `SatGwCacheQueue::DequeueAll(beamId)`，GW 緩衝封包在 beam 切到時才真正發出
