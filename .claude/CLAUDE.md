# CLAUDE.md — Claude Code 行為規範

本文件定義 Claude Code 在本專案中的工作方式與回覆規則，必須嚴格遵守。

---

## 1. 基本原則

### 1.1 不執行任何指令
Claude Code 僅負責撰寫、修改、整理與說明檔案內容。

禁止事項：
- 不呼叫 shell 指令
- 不執行編譯
- 不執行測試
- 不模擬執行結果
- 不自行啟動任何工具鏈或建置流程

使用者的開發環境為：
- Windows
- VS Code + Claude Code

實際執行流程為：
- Claude Code 直接修改 VS Code 工作區中的檔案
- 使用者再手動複製到 VMware 上的 SNS3 環境中執行

因此，Claude Code 的任務是：
- 改檔
- 補註解
- 整理架構
- 撰寫 guide / spec / prompt / code
- 說明修改範圍與預期結果

不是：
- 幫忙執行
- 幫忙驗證
- 幫忙編譯
- 幫忙跑模擬

## 3. Guide 文件規則

Guide 不只是說明文件，而是：

**讓人看完後可以立刻理解整體架構，並依照內容開始實作的文件。**
因此 Guide 必須具備：
- 程式運作的流程圖（用draw.io或mermaid畫）
- 架構背景
- 模組切分
- 資料流或控制流
- 關鍵 class / function 職責
- 實作順序
- 檔案落點
- 已知限制
- 後續擴充方向

Guide 不可只停留在概念描述，必須具有明確的落地性。

## 4. 改 code 的回覆規則

### 4.1 先說明，再給程式碼
每次提供程式碼前，必須先用一段文字清楚說明：

1. 改了哪個檔案
2. 改了哪個函式、類別或區塊
3. 這次修改的目的
4. 預期執行後會看到什麼輸出、行為或差異

不可一上來就直接貼程式碼。

---

### 4.2 改動範圍要明確
如果一次涉及多個檔案：
- 必須逐一列出
- 每個檔案分開說明
- 不可把多個檔案內容混在一起貼
- 不可讓使用者自己猜哪段屬於哪個檔案

建議格式如下：

- 檔案 A：修改內容、目的、預期效果
- 檔案 B：修改內容、目的、預期效果
- 檔案 C：修改內容、目的、預期效果

然後再分檔貼出程式碼。

---

### 4.3 一定要寫註解
所有新增或修改的程式碼都必須包含適當註解。

註解要求：
- 說明這段邏輯在做什麼
- 為什麼這樣做
- 與哪個模組或流程有關
- 避免只寫表面描述

不可只貼無註解程式碼。

---

### 4.4 不可假裝已執行
由於 Claude Code 不執行任何指令，因此不可以寫出以下類型內容：
- 「我已經測試過」
- 「執行後確認可正常運作」
- 「編譯成功」
- 「模擬已通過」

如果要描述預期結果，必須明確寫成：
- 預期會看到
- 理論上應該出現
- 依此修改後，使用者執行時應可觀察到

### 4.5 測試指令
- 有變更程式碼就要附上新的測試指令

## 5. 設計規則

### 5.1 採用 OOP
所有參數、狀態與控制流程應遵循 OOP 設計。

要求：
- 盡量放入 class / struct / config object 管理
- 避免散落的 hard code
- 避免把常數直接寫死在流程中
- 優先使用可擴充的成員、參數物件、設定類別

---

### 5.2 不確定就先問
如果遇到以下情況，先提出問題，不要自行假設：

- 介面不確定
- 類別責任不清楚
- 路徑歸屬有歧義
- 兩種以上設計方案都可能成立
- 需要選擇 naming、hook 點、資料流方向
- 不確定是否可修改某個 SNS3 原始碼檔案

原則是：

**不要自己發明接口，不要自己補規格，不要自己替使用者做未確認的設計決策。**

---

### 5.3 不動 SNS3 原始碼
原則上不得修改 SNS3 原始碼，也就是：

`contrib/satellite/` 下的原生檔案不可直接改動

除非：
1. 使用者明確提出
2. 已經討論過原因
3. 已取得確認

---

### 5.4 已允許修改的 SNS3 檔案
目前已確認可以改動的 SNS3 檔案只有：

- `satellite-sgp4-mobility-model.h`
- `satellite-sgp4-mobility-model.cc`
  - 已加入 `GetGeoPositionAt`

- `satellite-isl-arbiter-unicast.h`
  - 已加入 `ClearNextHopEntries`

除上述項目外，若要再修改其他 `contrib/satellite/` 內檔案，必須先說明：
- 為什麼一定要改
- 不改會卡在哪裡
- 是否存在非侵入式替代方案

未經確認不得直接動手。

## 6. 建議的回覆格式

當使用者要求改 code 時，Claude Code 應優先使用以下格式回覆：

### 6.1 若先提供設計或修改方案
1. 修改範圍
2. 涉及檔案
3. 每個檔案要改的函式 / 類別
4. 修改目的
5. 預期輸出或行為變化
6. 再貼程式碼

---

### 6.2 若規格仍不清楚
先列出不確定點，再等使用者確認，例如：
- 這個功能要放 Layer 1 還是 Layer 2？
- 這個 class 應該掛在 helper 還是 controller？
- 這個接口要沿用既有 callback 還是新建 wrapper？

---

### 6.3 若是文件類工作
若使用者要的是：
- guide
- spec
- prompt
- 工作日誌
- markdown 文件

則文件必須：
- 有清楚標題與分節
- 可直接放入專案資料夾
- 可直接作為後續實作依據
- 不寫模糊結論
- 不只寫概念，必須寫到可執行的程度

---

## 7. 專案工作原則總結

Claude Code 在本專案中的角色是：

**檔案設計者、程式碼修改者、架構整理者、文件撰寫者。**

Claude Code 不是：
- 編譯器
- 測試執行者
- shell 操作者
- 自動驗證器

所有輸出都必須符合以下原則：
- 路徑正確
- 分層正確
- 註解完整
- 修改範圍清楚
- 預期結果說明清楚
- 有疑問先問
- 不亂改 SNS3 原始碼
- 以可實作、可接續、可維護為優先
